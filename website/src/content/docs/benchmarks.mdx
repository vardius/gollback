These numbers measure gollback alone: the functions return at once, so what's left is the cost of starting goroutines,
collecting results and cancelling. Your functions will dominate a real call; the point is that gollback adds as little as possible.

In every race, one function wins at once and the others wait to be cancelled, as the slower replicas of a real
request do. With 16 callers or goroutines at once, the time is wall time per call across all of them, so it measures
throughput, not the latency of one call.

v1 started a goroutine to collect each race and sent every result through a channel; v2 starts one goroutine per
function and nothing else, and keeps results in one place behind a lock. `All` runs its first function on your
goroutine, so `All` of one function no longer starts a goroutine at all.

<Aside title="Where the allocations go">
`Retry` allocates nothing. `All` allocates the two slices it returns and, for more than one function, the state its
goroutines share. `Race` allocates its state, the context it cancels, that context's cancel func, and its channel.
Beyond that, each goroutine costs one small allocation: the Go runtime's, for the arguments of a `go` statement.
Handing work to long-lived goroutines through a shared queue would avoid it, but a prototype that did was slower
once many callers raced at the same time, so gollback pays it.
</Aside>

## Run them yourself

From a clone of the repository:

```sh
go test -run '^$' -bench . -benchmem
```

To compare two versions, run each a few times and compare with [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat):

```sh
go test -run '^$' -bench . -count 10 > new.txt
benchstat old.txt new.txt
```

The allocation counts are also enforced by tests: `TestAllocations` fails if a call allocates more than it should.
